
MUROORA MART — MASTER BUILD PROMPT FOR CLAUDE + CODEX
Version: 1.0
Purpose: Turn the existing Muroora Mart website into the first version of a real Zimbabwean e-commerce + local delivery platform, while preserving the current brand and keeping the architecture ready for future third-party merchants.

======================================================================
0. IMPORTANT CONTEXT
======================================================================

Muroora Mart is NOT a hypothetical project.

It is an operating retail business in Zimbabwe with its own stock and physical shop operations.

The current website already exists and should be treated as the visual/brand foundation. Do not rebuild the entire website from scratch unless absolutely necessary.

The short-term goal is:

1. Sell Muroora Mart's own inventory online.
2. Allow customers in Zimbabwe and the diaspora to order goods for recipients in Zimbabwe.
3. Allow Muroora Mart staff to receive, prepare and manage orders.
4. Build a delivery system using verified delivery partners/riders, preferably motorcycle owners.
5. Pay riders based on completed deliveries rather than assuming a fixed monthly salary model.
6. Provide proper order tracking, delivery status, proof of delivery and rider accountability.
7. Keep the underlying architecture capable of supporting third-party businesses later, but DO NOT turn the first release into an open marketplace.

The long-term direction is:

Muroora Mart -> Muroora Delivery -> Muroora local-commerce platform.

The system must therefore be future-proof without being over-engineered.

22. PROOF OF DELIVERY
======================================================================

Options:

A. Delivery OTP
B. Recipient signature
C. Delivery photo
D. Admin-confirmed exception

Recommended Version 1:
OTP + optional photo.

Process:

1. Customer/recipient receives OTP.
2. Rider arrives.
3. Rider enters OTP.
4. Order marked delivered.

Never allow riders to simply mark expensive orders delivered without a verifiable trail.

47. TESTING REQUIREMENTS
======================================================================

Create automated tests appropriate to the stack.

Critical test scenarios:

1. Customer adds in-stock product to cart.
2. Stock cannot become negative.
3. Customer can order for another recipient.
4. Unsupported delivery zone is rejected.
5. Order total calculation is correct.
6. Delivery fee calculation is correct.
7. Payment callback cannot duplicate payment.
8. Staff can progress order.
9. Unauthorized users cannot access admin.
10. Rider cannot access another rider's private account.
11. Customer cannot access another customer's order.
12. Rider cannot see unrelated customer addresses.
13. Unapproved rider cannot go online.
14. Rider with expired mandatory document cannot go online.
15. Delivery cannot complete without configured proof/exception process.
16. Completed delivery generates rider earnings exactly once.
17. Repeated API calls do not duplicate rider earnings.
18. Payout cannot exceed available balance.
19. Sensitive files are not public.
20. Audit log created for sensitive admin changes.

======================================================================
48. IDEMPOTENCY
======================================================================

Anything involving money, status changes or external callbacks must be designed to avoid duplication.

Examples:

- payment callbacks
- rider earnings creation
- refunds
- payout processing
- delivery completion

Use idempotency keys or database constraints where appropriate.

49. PERFORMANCE
======================================================================

Do not prematurely optimize.

However:

- paginate admin tables
- optimize images
- lazy-load where appropriate
- index frequently queried database fields
- avoid N+1 database queries
- cache non-sensitive catalogue data where appropriate

======================================================================
55. PWA / MOBILE
======================================================================

If compatible with the current stack, make the customer and rider interfaces installable as PWAs.

Rider experience especially must work well on inexpensive Android phones.

Consider:

- low bandwidth
- intermittent connectivity
- large tap targets
- offline-safe status retry where possible
- compressed images
- simple navigation

Do not assume every rider has a high-end device.

70. FINAL PRINCIPLE
======================================================================

Do not build Muroora as a pretty prototype.

Build it as a small, real operational commerce system that happens to have the architecture to become something much larger.

Muroora Mart is the first merchant and the proving ground.

The first target is not "become Meituan."

The first target is:

A customer places a real order.
The shop fulfils it.
A verified rider delivers it.
The customer knows what is happening.
The rider gets credited correctly.
The business can account for everything.

Once that works reliably, expansion becomes a business decision rather than a software fantasy.
