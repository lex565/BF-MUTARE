MUROORA STAFF INTERFACE — COMPLETE CODEX IMPLEMENTATION PROMPT

ROLE

You are implementing the staff-facing operational interface for Muroora.

This is NOT a customer shopping interface.
This is NOT the rider interface.
This is NOT a separate application/backend.

The staff interface must be built into the EXISTING Muroora platform and reuse the existing backend, database, authentication, products, inventory, orders, deliveries, riders, permissions, audit logs and visual design system wherever possible.

The main objective is simple:

A shop employee should open Muroora on their phone and immediately understand what work needs to be done.

The interface must be:
- fast
- mobile-first
- simple
- operational
- secure
- low-bandwidth friendly
- easy for non-technical staff
- consistent with Muroora branding

DO NOT overbuild this into enterprise software.

============================================================
1. FIRST ACTION — AUDIT WHAT ALREADY EXISTS
============================================================

Before writing code, inspect the existing Muroora repository and identify:

- current staff routes/pages
- current staff authentication
- current role-based permissions
- employee/profile model
- current order model
- order statuses
- inventory model
- product model
- delivery/rider handover model
- audit-log architecture

- existing design tokens/components
- existing Supabase configuration
- existing responsive/mobile patterns

Report each relevant staff feature as:

IMPLEMENTED
PARTIALLY IMPLEMENTED
NOT IMPLEMENTED
NEEDS REVIEW

Do not rebuild working functionality unnecessarily.

============================================================
2. MAIN STAFF PURPOSE
============================================================

The staff interface should help shop employees:

1. see new orders
2. accept an order
3. pick products
4. report unavailable/damaged/missing items
5. pack orders
6. mark orders ready for delivery
7. hand orders to riders
8. check stock
9. report stock issues
10. later process counter sales
11. view their own activity
12. report operational issues

The interface should answer:

WHAT NEEDS MY ATTENTION RIGHT NOW?

============================================================
7. ACCEPT ORDER
============================================================

A new order should be explicitly accepted by a staff member.

Workflow:

NEW ORDER
→ ACCEPT ORDER
→ employee ID recorded
→ timestamp recorded
→ order assigned to employee
→ status becomes ACCEPTED / PREPARING according to existing state model

Do not silently assign an order without a clear record.

If multiple staff members are viewing the same order, prevent accidental double acceptance.

Use appropriate server/database-side checks.

============================================================
8. PICKING WORKFLOW
============================================================

Once order picking starts:

Show progress such as:

4 / 6 items picked

The employee should be able to:

- mark item picked
- adjust to correct required quantity where the workflow allows
- mark item unavailable
- report item issue

Example:

PICKING ORDER #MUR-1042

✓ Cooking Oil ×2
✓ Sugar ×1
✓ Mazoe ×1
□ Bread ×2

4 / 6 items

[ITEM UNAVAILABLE]
[COMPLETE PICKING]

Do not allow staff to mark picking complete when mandatory item states remain unresolved.

============================================================
9. ITEM UNAVAILABLE / STOCK ISSUE FLOW
============================================================

This needs to be easy because it will happen in a real shop.

When employee taps UNAVAILABLE, ask:

WHAT HAPPENED?

- Out of stock
- Stock count incorrect
- Damaged
- Cannot locate item
- Wrong product data
- Other

Then:

WHAT SHOULD HAPPEN?

- Remove item from order
- Suggest substitute
- Ask supervisor/admin
- Hold order for review

Only offer actions supported by the existing backend/order/refund rules.

Do not let ordinary staff arbitrarily change customer charges unless authorized.

Record:
- employee
- product
- reason
- timestamp
- order
- resolution

============================================================
10. SUBSTITUTIONS
============================================================

If substitution already exists in the backend, design a clean staff workflow around it.

If it does not exist, do NOT invent complex substitution payment logic without explaining the required backend changes first.

Possible flow:

Original item unavailable
→ staff suggests alternative
→ customer/admin approval where required
→ substitution recorded
→ pricing difference handled by existing approved rules

All substitutions must be auditable.

Do not let staff skip required order states without authorized override.

14. CHAIN OF CUSTODY

→ RIDER ASSIGNED

→ HANDED TO RIDER

Do not duplicate custody logic in frontend code.

============================================================
22. STAFF ACCOUNT CREATION / ACTIVATION
============================================================

Public users must never be able to register and choose SHOP_STAFF.

Preferred current flow:

Employee creates normal account
→ admin identifies account
→ admin assigns SHOP_STAFF role
→ staff access becomes active

or use the existing secure invitation flow if already implemented.

There should be no shared staff login.

Each employee gets an individual account.

============================================================
23. ROLE-BASED PERMISSIONS
============================================================

At minimum support appropriate distinctions between:

SHOP_STAFF
SUPERVISOR / MANAGER where already planned
ADMIN / OWNER

SHOP_STAFF may perform operational functions such as:

- view assigned/relevant orders
- accept orders
- pick
- pack
- report issues
- confirm rider handover
- check stock
- request permitted stock changes

SHOP_STAFF must NOT automatically be able to:

- change their own role
- create admins
- modify merchant commission
- change rider trust limits
- view sensitive rider verification documents
- delete historical sales/orders
- erase audit logs
- change backend/payment credentials
- arbitrarily edit completed orders
- approve high-risk refunds
- access sensitive financial reports unless explicitly allowed

Enforce permissions server-side/database-side, not merely by hiding buttons.

============================================================
27. LOW-BANDWIDTH / MOBILE REQUIREMENTS
============================================================

Employees may use their own phones.

Design for:

- Android mobile browsers
- lower-cost phones
- slow/intermittent connections
- one-handed use
- large buttons
- readable text
- minimal typing
- clear loading states
- retry states
- no unnecessary large images
- no autoplay video
- no heavy animation

Critical actions should be resilient to accidental refreshes/retries.

============================================================
28. OFFLINE / CONNECTION FAILURE BEHAVIOUR
============================================================

Do not pretend the network will always work.

At minimum:

- show connection status clearly when actions fail
- do not silently lose work
- prevent duplicate order acceptance/packing actions caused by retries
- use idempotent backend operations where appropriate
- allow safe retry
- clearly distinguish "saved" vs "not saved"

Do not build a complex full offline-first system unless genuinely needed.

============================================================
29. ERROR STATES
============================================================

Design proper states for:

- no orders
- failed to load orders
- order already accepted by another employee
- product unavailable
- stock mismatch
- rider not assigned
- rider handover failed
- permission denied
- session expired
- server error
- poor network

Never show raw technical stack traces to staff.

============================================================
30. SECURITY
============================================================

Never expose:

- Supabase service-role key
- backend secrets
- payment credentials
- private customer data unrelated to the active order
- private rider verification documents
- merchant financial information
- admin-only configuration

Use existing RLS/server authorization.

Do not trust role checks performed only in the browser.

============================================================
31. DATABASE CHANGES
============================================================

Before making database changes:

1. inspect existing tables
2. reuse current order/inventory/staff tables
3. avoid duplicates
4. explain proposed migration
5. preserve existing data
6. ensure constraints prevent impossible workflow states

Possible missing concepts may include:

- staff profile
- staff public ID
- employee assignment on orders
- order item fulfilment states
- staff operational issue reports
- stock adjustment requests
- audit events

These names are conceptual only.

Use existing naming conventions.

============================================================
32. DESIGN LANGUAGE
============================================================

Use the existing Muroora design system.

Visual direction:

- dark Muroora green
- orange action accents

- large action buttons

============================================================
37. FINAL PRINCIPLE
============================================================

The staff interface should feel like a tool employees use to complete real work quickly.

The employee should be able to open Muroora and immediately answer:

WHAT ORDER DO I NEED TO HANDLE?
WHAT DO I PICK?
WHAT IS MISSING?
IS IT PACKED?
WHO AM I HANDING IT TO?
HAS MY ACTION BEEN RECORDED?

Keep the experience simple.

CUSTOMER MUROORA = SHOPPING
RIDER MUROORA = DELIVERY
STAFF MUROORA = GET THE WORK DONE
OWNER MUROORA = CONTROL AND UNDERSTAND THE BUSINESS
